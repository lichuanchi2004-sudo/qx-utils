# 大西洋（The Atlantic）正文插图显示灰块 —— 排查结论

排查日期：2026-10-14　范围：先只排查（第一~四节），后按用户要求修复（第五节，`atl_reader.js` v4）

---

## 一、结论（一句话）

**脚本赌错了"懒加载"的实现方式。** 大西洋的正文插图 **不是** `data-src` 那套懒加载，
它的 `src` / `srcset` 服务端下发时本来就是对的；图片看不见是因为
**CSS 里写着 `.Image_lazy__hYWHV{opacity:0}`**，要等站点自己的 JS 在图片 `load` 后
挂上 `Image_loaded__zmzJ7` 才淡入。脚本删掉了全部 `<script>`，这两个类永远加不上，
于是只剩外层的灰色占位框。脚本重写 `src/srcset` 完全是打偏的。

---

## 二、证据链（全部来自真实的线上 HTML / CSS，非推测）

### 取证方式
沙箱直连、无头 Chrome、Wayback、Common Crawl、jina 全被 Cloudflare 拦（`/feed/`、`/robots.txt`
放行；jina 拿到的是 "Please hold a moment"）。
最终用 **microlink 的 `data.html.attr=html` + `javascript=false`** 拿到
**未执行 JS 的服务端 SSR HTML（290KB）**，再直接下载大西洋 Next.js 的 CSS 文件核对类名。

### 1. 服务端下发的正文图，`src`/`srcset` 本来就是正确的

```html
<figure class="ArticleInlineFigure_figure__qmYhH" style="--imageWidth:928px;max-width:928px">
  <picture class="ArticleInlineImagePicture_picture__SVXJ7" style="padding-bottom:79.96%">
    <img alt="…" loading="lazy"
         class="Image_root__XxsOp Image_lazy__hYWHV ArticleInlineImagePicture_image__I79fR"
         sizes="(min-width: 982px) 928px, …"
         srcset="https://cdn.theatlantic.com/thumbor/Rw3SmF…/640x512/media/img/posts/2025/05/… 640w, … 928w"
         width="928" height="742">
  </picture>
</figure>
```

- `<img>` 有**真实 `src`**（见下）和**完整 `srcset`**，`width`/`height` 齐全。
- 整页 **`data-src` 属性 = 0 个**（唯一一处 `data-src` 出现在内联 `<style>` 的广告拦截选择器里）。
  ⇒ 脚本里那一整套 `data-src / data-lazy-src / data-original / data-bg` 还原逻辑，
  **在这个站点上一条都没命中**。

### 2. 真正的原因是 CSS 类：`opacity:0`

`cdn.theatlantic.com/_next/static/css/5bbd21a2868cbe11.css`：

```css
.Image_root__XxsOp { width:100%; height:auto; display:block }
.Image_lazy__hYWHV { opacity:0 }                                  /* ← 图片初始不可见 */
.Image_loaded__zmzJ7 { opacity:1; transition:opacity .3s }        /* ← 只有 JS 会挂上 */
```

`Image_loaded__zmzJ7` 是**站点自己的 React 组件在图片 load 回调里加的**。
删掉全部脚本 ⇒ 永远加不上 ⇒ 图片永远 `opacity:0`。

### 3. 灰块的来源：占位底色 `#c0ccda`

```css
.ArticleInlineImagePicture_picture__SVXJ7{
  background-color: var(--article-image-loading-placeholder-color);
  display:block; width:100%; height:0; overflow:hidden;
  padding-bottom:56.25%;        /* 行内还会覆盖成 79.96% / 100% / 116.95% —— 预留等比框 */
  position:relative;
}
.ArticleInlineImagePicture_picture__SVXJ7.ArticleInlineImagePicture_loaded__EFdMd{
  background-color: initial;    /* 加载完成后清掉灰底（同样是 JS 加的类） */
}
--article-image-loading-placeholder-color: #c0ccda;
```

⇒ 你看到的"灰块" = 这个 `padding-bottom` 撑出来的、底色 `#c0ccda` 的等比框。

### 4. 为什么"首图不灰、下面的图灰"（完全对得上）

| | class | 是否含 `Image_lazy__hYWHV` | 结果 |
|---|---|---|---|
| 首图 | `Image_root__XxsOp ArticleLeadArt_image__HZS4B` | **否** | 正常显示 |
| 正文插图 | `Image_root__XxsOp **Image_lazy__hYWHV** ArticleInlineImagePicture_image__I79fR` | **是** | `opacity:0` → 灰块 |

### 5. 实测：把 `atl_reader.js` 跑在真实 SSR HTML 上，它没碰到病因

| 指标 | 输入 | 输出 |
|---|---|---|
| `<script>` | 多 | **0**（全删） |
| `Image_lazy__hYWHV` | 12 | **12（一个没少）** |
| `loading="lazy"` | 12 | **12（没动）** |
| `<img>` | 15 | 15（结构完好） |

即：脚本删了脚本、又去重写本来就正确的 `src/srcset`，**唯独没有处理 `opacity:0` 这个真正的病根**。

## 三、顺带发现：大西洋自己的打印样式表里就是正解

在 CSS 的 `@media print`（已用括号深度定位确认）中：

```css
@media print {
  .ArticleInlineImagePicture_image__I79fR{ position:static!important;max-width:100%!important;
      height:auto!important; opacity:1!important; display:block!important }
  .ArticleInlineImagePicture_picture__SVXJ7{ height:auto!important;padding-bottom:0!important;
      background-color:initial!important;overflow:visible!important }
}
```

所以 Safari「打印 / 存为 PDF」时插图是正常的。
这也说明**要修的话，最省事的做法是照抄站点自己的打印样式**（把 `opacity:1` 和
`background-color:initial` 提到非 print 场景），而不是继续去还原 `data-src`。

> 按你的要求，本次只排查、未改动 `atl_reader.js`。

## 五、修复（2026-10-14 已实施，`atl_reader.js` v4）

照抄站点自己的打印样式思路，把"等 JS 来改"的样式直接写成终态，注入到 `<head>` 最前：

```css
/* (a) 所有懒加载图：站点 JS 没了，直接可见（正文插图/作者头像/杂志封面/QuickLinks 共 12 张） */
[class*="Image_lazy__"]{ opacity:1!important; transition:none!important }

/* (b) 正文插图外层 <picture>：height:0 + padding-bottom 的灰框就是"灰块本体"，取消掉 */
[class*="ArticleInlineImagePicture_picture__"]{
  height:auto!important; padding-bottom:0!important; padding-top:0!important;
  background-color:transparent!important; background-image:none!important; overflow:visible!important
}

/* (c) 正文插图本体 <img>：height:100% 相对父的 0 高会把图压成 0，改回自然撑开 */
[class*="ArticleInlineImagePicture_image__"]{
  position:static!important; height:auto!important; width:auto!important;
  max-width:100%!important; opacity:1!important; display:block!important
}

/* (d) 兜底：任何原生懒加载图不得因 opacity 不可见 */
img[loading="lazy"]{ opacity:1!important }
```

选择器全部用**类名前缀子串匹配**（`[class*="Image_lazy__"]`）而非写死哈希（`Image_lazy__hYWHV`）——
站点重新构建后哈希会变，前缀匹配则长期有效。

### 实测验证（真实 SSR HTML + 无头 Chrome）

计算样式对比（取第一张正文插图）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `<img>` opacity | **0** | **1** |
| `<picture>` padding-bottom | **408.59px** | **0px** |
| `<picture>` background-color | **rgb(192,204,218)** ← 灰块 | **rgba(0,0,0,0)** |
| 懒加载类元素 opacity | **0** | **1** |

页面渲染对比：`atl_图片修复_前.png`（3.6KB，纯 `#c0ccda` 灰块）
→ `atl_图片修复_后.png`（114KB，画作正常）；三图合并版
`atl_正文插图_修复前_全部灰块.png` → `atl_正文插图_修复后_全部出图.png`。

回归检查（不应有副作用）：正文字数与段落数**前后完全一致**（86 个 `<p>`、约 7562 词），
`<script>` 归零，首页脚本（`atl_home.js`）未受影响。

> 注：`atl_home.js` 首页脚本本次**未改动**。

## 四、附：脚本里那条 CSS 的一个隐藏风险（同因）

`atl_reader.js` 注入的 CSS 用的是模糊匹配：

```css
[class*="paywall"],[class*="Paywall"],… { display:none!important; visibility:hidden!important; height:0!important; overflow:hidden!important }
```

大西洋的类名是 CSS Modules 带哈希的（`Image_root__XxsOp` 这类），**没有** `paywall` 字样，
所以这条暂时没造成误伤。但它和新版纽约客脚本踩过的坑是同一个类型
（`[class*="paywall"]` 把正文 `<p class="paywall">` 一起藏了）——
如果以后大西洋的类名里出现 `paywall/blur/fade` 之类的词，这种模糊匹配会直接隐藏正片内容。
